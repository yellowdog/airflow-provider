# YellowDog Airflow Provider 2.0 — Workflow-Level Operators, Deferral, Cancellation and Safe Retries

**Date:** 2026-11-11
**Branch:** `provider-2.0-workflow` (from `next-version` at `ab289a1`)
**Target release:** 2.0.0 (unreleased; breaking changes are still allowed)
**Builds on:** `docs/superpowers/specs/2026-11-10-provider-2.0-quality-program-design.md` (its constraints and anti-goals still apply)

## Intent

The provider integrates YellowDog with Airflow correctly but at too low a level. It mirrors the YellowDog SDK call-for-call, so DAG authors assemble the YellowDog lifecycle themselves: the full example DAG needs ~14 tasks plus six `TriggerRule.ALL_DONE` clean-up tasks to "provision a pool, run work on it, shut it down".

The user's picture of a typical first DAG is exactly that: **provision a pool, run work on it, then shut it down.** 2.0 should make that a three-task DAG that is safe by construction:

```python
pool = ProvisionWorkerPool(..., wait_until_ready=True).as_setup()
run = RunWorkRequirement(work_requirement=..., task_groups_and_tasks=...)
stop = ShutdownProvisionedWorkerPool(..., wait=True).as_teardown(setups=pool)
pool >> run >> stop
```

Why now: the user prefers to put everything into 2.0 because making a release has friction, and 2.0 is expected to ship soon. (User decision.)

## Goals

1. **`RunWorkRequirement` operator** — submit a populated work requirement, wait for it, succeed on COMPLETED, fail on a failure state (using the existing `failure_states` semantics and `YellowDogStateError`), cancel on kill, retry safely.
2. **Deferrable waiting** — every waiting step can defer to a trigger so long HPC jobs don't hold Airflow worker slots.
3. **Cancellation on kill** — stopping/failing/timing out a task in Airflow cancels the YellowDog work it started.
4. **Safe (idempotent) retries** — a retry never fails on a duplicate name and never leaves a half-built work requirement behind.
5. **Worker pool as setup/teardown** — provision waits for readiness; shutdown waits for completion; examples use Airflow's `as_setup()` / `as_teardown()`.
6. **Operations on the hook** — reusable from TaskFlow `@task` code; operators become thin.
7. **Portal links** — "View in YellowDog Portal" extra links on tasks.
8. **SDK objects via XCom** — investigate and, if it works, support passing SDK objects from upstream `@task`s; keep callables as an alternative either way.

## Non-goals

- Removing or renaming the existing fine-grained operators/sensors (`AddWorkRequirement`, `AddTaskGroupsToWorkRequirement`, `AddTasksToTaskGroup`, `AddPopulatedWorkRequirement`, `CancelWorkRequirement`, `ProvisionWorkerPool`, `ShutdownProvisionedWorkerPool`, the three sensors). They stay; they gain deferral/cancel/retry behaviour where it fits.
- Removing the `(context, jinja_env)` callable convention (user: keep as an alternative).
- Portal links for compute requirements or task groups.
- Object store support (project principle).
- Changing Python/Airflow/SDK support ranges (Airflow ≥ 3.1, Python 3.12–3.14, yellowdog-sdk ≥ 15.10.0).

## Anti-goals (failure even if it "works")

- Anything that can leave a worker pool or work requirement running after the DAG run ends, including after a failure, a kill, or a retry.
- Deferral that silently hangs: a deferred task must never wait forever without a timeout, and the default must be safe for deployments without a triggerer.
- Breaking what is already in 2.0 (failure states, typed keyword-only API, id-or-name lookups, templating rules, `YellowDogArgumentError` on `"None"` IDs).
- Weakening the quality gates: pyright strict for `yellowdog_provider/`, `bin/verify_types.py` passing, `make check` green at Airflow min and max, docs `-W` clean, plain `pytest`/CI never touching the platform.
- Catching SDK exceptions other than the documented tolerances (YEL-13327 "invalid transition" on cancel; the new kill-path best-effort cancel below).

## Priorities (user decision)

If time runs short, drop **Portal links** first, then **hook methods**. Everything else is required for 2.0.

## Decisions

### Core workflow shape (user approved)
- The three-task shape above is the recommended pattern and becomes the quickstart and the main example.
- `RunWorkRequirement` takes the same inputs as `AddPopulatedWorkRequirement`: `work_requirement` (a `WorkRequirement`, templated / callable / XCom — see below) and `task_groups_and_tasks` (list of `(TaskGroup, list[Task])`). Plus `target_states` (default `[COMPLETED]`), `failure_states` (same defaulting as the sensors), `poke_interval`, `timeout`, `deferrable`, `connection_id`. Returns the work requirement ID (XCom `return_value`).
- `ProvisionWorkerPool` gains `wait_until_ready: bool = False` (when true, waits until the pool is `IDLE` or `RUNNING` — i.e. workers have registered; EMPTY/PENDING/CONFIGURING are not ready, so a pool whose instances never come up fails at the timeout, which is correct because no work could run *(controller's call)*; fails via failure states if it reaches SHUTDOWN/TERMINATED first), plus `poke_interval`, `timeout`, `deferrable`. Default `False` keeps today's behaviour. *(Builder may change the default to `True` if it reads better in the examples; record the choice in the changelog.)*
- `ShutdownProvisionedWorkerPool` gains `wait: bool = False` (when true, waits until the pool is SHUTDOWN/TERMINATED, and, with `terminate_immediately`, until its compute requirement is TERMINATED), plus `poke_interval`, `timeout`, `deferrable`. Default `False` keeps today's behaviour.

### Deferral (controller's call; user: deployment types unknown)
- Every waiting step — `RunWorkRequirement`, `ProvisionWorkerPool(wait_until_ready=True)`, `ShutdownProvisionedWorkerPool(wait=True)`, and the three sensors — takes `deferrable: bool = conf.getboolean("operators", "default_deferrable", fallback=False)`, Airflow's own convention. Off unless the deployment's administrator turns it on globally or the DAG sets it.
- Off: waiting polls every `poke_interval` (operators) / per sensor mode (sensors, incl. `mode="reschedule"`).
- On: a trigger polls YellowDog status from the triggerer and resumes the task only on a target state, a failure state, or timeout. Failure states, timeouts, XCom of IDs and Portal links behave identically in both modes.
- The SDK is synchronous; the trigger runs each status call in a thread (e.g. `asyncio.to_thread` / `sync_to_async`) and creates/closes its own client from the connection ID. Triggers must be serialisable (`serialize()` with the connection ID, resource ID, states as values, poke interval, deadline).
- `YellowDogStateError` currently inherits `AirflowException.serialize()` (message only). If any failure crosses the trigger boundary as an exception, give it a working serialization; otherwise the trigger yields an event and the task raises in `execute_complete`.
- Docs: recommend turning deferral on wherever a triggerer runs; explain the default.

### Cancellation on kill (user: abort straight away)
- `RunWorkRequirement`, `AddWorkRequirement`, `AddPopulatedWorkRequirement`: `on_kill` cancels the work requirement they created **with abort running tasks = true**. In deferred mode, the equivalent cleanup runs when the deferred task is killed (builder: use Airflow 3's mechanism for this — e.g. trigger `cleanup()`/cancellation handling or the operator's kill path — and verify at Airflow 3.1 and 3.4; if Airflow cannot run cleanup for a killed deferred task on some version, document the gap and rely on teardown/sweep).
- `ProvisionWorkerPool` killed while waiting for readiness: shut the pool down (terminate). A pool that is already ready is **not** touched by killing other tasks — the setup/teardown pairing owns it.
- Kill-path cancellation is best-effort: log failures, never raise; an already-finished resource is ignored (existing "invalid transition" tolerance).
- To know what to cancel, an operator must record the ID it created before it starts waiting (instance attribute and XCom).
- **Own timeout / failure also cleans up** *(controller's call, follows from the "nothing left running" anti-goal)*: when `RunWorkRequirement` (or `AddPopulatedWorkRequirement` if it waits) gives up on its own `timeout`, it cancels its work requirement with abort = true before failing — the same as Airflow's `execution_timeout`, which already calls `on_kill()`. A retry then submits a fresh `-try<N>` copy. "Resume waiting" (below) therefore only applies when the previous attempt ended without any cleanup (e.g. a worker crash).
- **Pools clean up after themselves** *(controller's call)*: if `ProvisionWorkerPool(wait_until_ready=True)` fails, times out or is killed before the pool is ready, it terminates the pool it created. A retry therefore never orphans a pool.
- **Fallback if Airflow cannot clean up a killed deferred task** (user approved): `ShutdownProvisionedWorkerPool` used as the teardown also cancels (abort = true) any unfinished work requirements stamped with the current DAG run (see the run stamp under "Safe retries"). This keeps the recommended DAG at three tasks and closes the gap regardless of Airflow version. Builder: implement this unconditionally (it is cheap and also covers crashed workers), behind a parameter such as `cancel_run_work_requirements: bool = True`, and scope it strictly to the stamp so it never touches other runs' work.

### Safe retries (user: fresh copy on failed/cancelled)
- `RunWorkRequirement` always knows the work requirement's name:
  - If the supplied `WorkRequirement.name` is set, use it.
  - If empty, derive one from DAG ID, task ID and run ID, sanitised to YellowDog rules (lowercase `a-z0-9_-`, ≤ 60 chars), shortening long parts with a short stable hash so names stay unique. *(Controller's call.)*
- **Run stamp** (user approved): every work requirement the provider submits is stamped with its origin — DAG ID, run ID, task ID, map index — in the work requirement's `tag` (builder: confirm the SDK `WorkRequirement.tag` field can hold it, within platform limits; if not, use another SDK field fit for this and document it). Only a work requirement carrying **this run's and this task's** stamp counts as "the previous attempt".
- On each attempt, look up existing work requirements by namespace + name (and `<name>-try<N>` variants) and apply:
  - none → submit;
  - same name but a **different stamp** (another run, or not created by the provider) → submit a fresh copy under a suffixed name (names must be unique) — never adopt it (user approved);
  - this run's stamp, not finished → **resume waiting on it** (do not resubmit);
  - this run's stamp, COMPLETED → succeed without resubmitting — **except after the task was cleared**: clearing a successful task re-runs the work as a fresh copy, matching Airflow's meaning of "clear" (user approved). Builder: distinguish "retry after failure" from "clear" (e.g. Airflow's try number vs. the stamped try number, or the task instance's previous state) and document the rule;
  - this run's stamp, FAILED or CANCELLED → **submit a fresh copy named `<name>-try<N>`** where N is Airflow's `try_number` (respect the 60-char limit);
  - this run's stamp but only partly built (fewer task groups / tasks than supplied) → **cancel it (abort) and submit a fresh `-try<N>` copy** *(controller's call)*.
- `AddPopulatedWorkRequirement` gets the same retry rules so a retry no longer fails on a duplicate name.
- The fine-grained `AddWorkRequirement` / `AddTaskGroupsToWorkRequirement` / `AddTasksToTaskGroup`: builder decides whether retry-safety applies; at minimum document their retry behaviour.

### Setup/teardown pools (user approved)
- Examples and docs use `.as_setup()` / `.as_teardown(setups=...)`. The full example DAG and the quickstart move to the three-task shape (the quickstart may assume an existing pool today — builder decides whether it becomes provision/run/shutdown or stays "run on an existing pool" with a second minimal pool example; the main example must show the three-task shape).
- The six `ALL_DONE` teardown tasks disappear from the main example.

### Hook methods (priority: drop second)
- `YellowDogHook` gains typed operations that the operators call: submit a populated work requirement (with the retry rules), get work requirement / worker pool / compute requirement status, cancel a work requirement (abort flag), provision a pool, shut down / terminate a pool, and wait helpers (poll until target/failure/timeout) usable from TaskFlow. Builder designs exact names/signatures; they must be strict-typed and documented in the API reference with a TaskFlow example.

### Portal links (priority: drop first)
- Operator extra links: "YellowDog work requirement" on `RunWorkRequirement`, `AddWorkRequirement`, `AddPopulatedWorkRequirement`, `WorkRequirementStateSensor`; "YellowDog worker pool" on `ProvisionWorkerPool`, `ShutdownProvisionedWorkerPool`, `WorkerPoolStateSensor`.
- URLs (user-supplied examples):
  - work requirement: `https://portal.yellowdog.ai/#/work/<work-requirement-id>`
  - worker pool: `https://portal.yellowdog.ai/#/workers/<worker-pool-id>`
- Portal base derived from the connection's Platform API URL by replacing a leading `api.` host label with `portal.` (user confirmed the rule holds for other environments), with an optional connection field "Portal URL" to override.
- A link appears once the ID is in XCom; no link otherwise.
- Register links in provider metadata (`extra-links` in `get_provider_info`) as Airflow requires.

### SDK objects via XCom (user: keep callables as an alternative)
- First implementation step: verify at Airflow 3.1 **and** 3.4 whether YellowDog SDK model objects (dataclasses: `WorkRequirement`, `TaskGroup`, `Task`, `RunSpecification`, `ComputeRequirementTemplateUsage`, `ProvisionedWorkerPoolProperties`, nested enums/timedeltas) round-trip through XCom from a `@task` into an operator's templated field.
- If yes: operators accept them (e.g. `work_requirement=build_wr()` where `build_wr` is a `@task`); docs show this as the primary pattern; callables documented as the alternative.
- If no (or only partly): keep callables as the way to build SDK objects at run time and say why in the docs. Do not add JSON/dict wrappers (project principle).

## Constraints

- Everything from the quality-program spec: Airflow ≥ 3.1 imports from Airflow 3 locations (`airflow.sdk`), version-conditional imports only where unavoidable and type-clean at min and max; pyright strict + verifytypes; SDK objects used directly; `make check` green at Airflow 3.1/Py3.12 and Airflow 3.4/Py3.14; CI unchanged in shape.
- Breaking changes allowed (2.0) but every one gets a changelog before/after entry.
- Live system tests (opt-in, never CI) and the e2e must keep run-tag naming and the cleanup sweep.
- Work on branch `provider-2.0-workflow`; squash-merge to `next-version` only with the user's OK.

## Testing (controller's call)
- Unit tests for all new behaviour (triggers with mocked hook, retry decision table, name derivation, kill paths, link URLs, Portal base derivation).
- Live component tests at Airflow 3.1 and 3.4 add: `RunWorkRequirement` non-deferred; a failure-state run; a retry after a failed work requirement (fresh `-tryN` copy); a name collision with another run's stamp (fresh suffixed copy, other run untouched); own-timeout → cancellation; kill → cancellation (simulate via `on_kill`); provision `wait_until_ready` and shutdown `wait`; teardown cancelling this run's unfinished work requirements only.
- Deferred mode can only be exercised for real under a scheduler + triggerer: the e2e (Airflow `standalone` runs a triggerer) runs the new three-task example DAG with deferral **on**, at both Airflow versions; plus a setup/teardown check that the pool is shut down when the run task fails (a second small DAG or a param that makes work fail).
- Every live run ends with no `systest-` resources left.
