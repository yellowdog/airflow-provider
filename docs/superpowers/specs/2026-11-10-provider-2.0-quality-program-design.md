# YellowDog Airflow Provider 2.0 — Quality Improvement Program

**Date:** 2026-11-10
**Branch:** `next-version`
**Target release:** 2.0.0

## Intent

Make the YellowDog Provider for Apache Airflow rock solid, well documented and
easy to maintain. This is proactive work driven by quality, completeness and
maintainability — not by a reported bug or an imminent customer need — so it
can be sequenced for long-term health rather than speed.

## Current state (as of 1.0.5)

- **No tests.** `tests/` contains only empty `__init__.py` files.
- **Airflow 2 compatibility shims** (`try/except ImportError`) in the hook,
  operators, sensors and example DAG; two Airflow 2 container scripts in `bin/`.
- **No type checking.** `mypy` is listed in dev requirements but unconfigured.
  `.pyi` stubs are generated by `stubgen` at build time (gitignored).
- **No CI.** No `.github/` directory.
- **Manual release** per `RELEASING.md`: bump version, tag, `twine upload`
  using `~/.pypirc`, build & push docs Docker image, notify ops.
- **Thin docs:** one `index.rst` plus autodoc pages; no tutorial, concept
  primers, troubleshooting or changelog.
- **Known defects** spotted in an initial read (see Code Review).
- `requires-python` is `>=3.10, <3.13`.

## Goals

1. Drop Airflow 2 support; require Airflow ≥ 3.1 and Python 3.10–3.13.
2. Thorough code review of the hook, operators, sensors, utils and exceptions,
   with fixes.
3. Type checking with pyright on the package; a fully typed public API that
   users can type-check against.
4. Comprehensive unit tests (no YellowDog platform access).
5. System tests against a real YellowDog account that provision real cloud
   instances: pytest-level component tests **and** a full-Airflow run of the
   example DAG.
6. A local configuration file holding credentials and settings for system
   tests.
7. GitHub Actions CI running unit-level checks automatically.
8. A local, automated release script.
9. Thorough documentation review and gap-filling for readers who may know
   Airflow, YellowDog, both, or neither.
10. Clearly captured breaking changes with a migration guide.

## Non-goals

- Object store support (explicitly excluded by project principles).
- `CONTRIBUTING.md` (not wanted at this time).
- Publishing from GitHub (release runs locally).
- Running system tests in CI.
- Changes to the untracked local `dag-test.py` — leave it in place, untouched.

## Anti-goals (would be failure even if it "works")

- Any plain `pytest` / CI run that touches the YellowDog platform or spends
  money.
- System tests that leave cloud instances or worker pools running after a
  failure.
- Breaking changes that aren't documented with a before/after migration note.
- Catching/swallowing SDK exceptions (contrary to the project's design
  principle — exceptions propagate to Airflow). Existing deliberate tolerance
  of idempotent cancellation (YEL-13327) may stay.
- Wrapping SDK objects in JSON/dict abstractions (contrary to design
  principles).

## Constraints & decisions made with the user

### Platform support
- `apache-airflow >= 3.1`, Python `>=3.10, <3.14`. Classifiers updated to
  match. (Decided after builder check: Airflow 3.0.x excludes Python 3.13 —
  PyPI `requires-python: !=3.13` — and does not export `BaseHook` from
  `airflow.sdk`. A 3.1 floor gives a clean matrix and zero compat code.)
- All Airflow imports use Airflow 3 locations (`airflow.sdk` etc.); remove all
  Airflow 2 fallbacks, `# type: ignore[no-redef]` shims, and
  `bin/start-airflow-2.*-container.sh`.
- Test against the **min and max of both axes**: Python 3.10 and 3.13 ×
  Airflow 3.1.x (lowest supported) and latest Airflow 3.x.

### API changes
- Breaking changes are allowed **if they are improvements**. Every one is
  recorded in the changelog under "Breaking changes / Migrating from 1.x" with
  a before/after example, and reflected in the docs.
- Version becomes **2.0.0**.
- **1.0.5 is skipped** (never released; its changes fold into 2.0.0). The
  changelog's 2.0.0 entry is relative to **1.0.4**, the last PyPI release.
- No 1.x maintenance branch; bugs found in review are **not** backported
  (builder's call, unobjected).

### Type checking & stubs
- Users must be able to type-check against the provider.
- Approach (agreed): keep `py.typed`, fully annotate the public API inline,
  **stop generating `.pyi` stubs with stubgen** (generated stubs shadow and can
  degrade the inline types), and enforce completeness with
  `pyright --verifytypes yellowdog_provider` in CI.
- Run `pyright` (strict mode for `yellowdog_provider/`) in CI.
- Remove the `stubs` Makefile target, stub references in `make build`/`clean`,
  the `*.pyi` gitignore entry rationale, and the CLAUDE.md section about stubs
  (update it).

### Unit tests
- pytest, no network; YellowDog `PlatformClient` mocked.
- Cover: hook (connection field handling, default URL, host empty/None,
  client caching, UI field behaviour, provider info entry point); every
  operator (happy paths, id-vs-name lookup, missing-argument errors, return
  values / XCom); every sensor (target reached / not reached, XCom push,
  id-vs-name); utils; templating of string fields **and** callable fields;
  example DAG imports/parses without errors (DagBag-style integrity test).
- Every bug fixed in code review gets a regression test.

### System tests
- Provision real cloud instances in a real YellowDog account.
- Two levels:
  1. **Component (pytest):** tests call operators/sensors directly against the
     live platform.
  2. **End-to-end (full Airflow):** start a real Airflow (building on
     `bin/start-airflow-container.sh`) and run the example DAG to success,
     exercising scheduler, XCom and templating together.
- Run **manually only**, never in CI.
- **Opt-in & safe by default:** skipped unless the system-test config file is
  present (and/or an explicit marker/flag is passed) so `pytest` alone never
  hits the platform.
- **Clean up always:** shut down/terminate worker pools and cancel work
  requirements in teardown, including after failures. Use unique, run-scoped
  names so concurrent or aborted runs don't collide and leftovers are
  identifiable.

### System test configuration file
- A local file holding the credentials and settings the system tests need;
  gitignored, with a committed example template beside it.
- Expected contents (builder may refine): Platform API URL, Application key ID
  and secret, namespace, compute requirement template (ID or name), and any
  sizing/timeout knobs needed to keep cost and duration bounded.
- The full-Airflow test uses the same file to create its Airflow connection
  (replacing reliance on `YD_VAR_APP_*` environment variables for testing).

### CI (GitHub Actions)
- Triggers: automatically on pushes to `next-version`. (Builder's call: also
  on PRs targeting `main`.)
- Jobs: lint/format check, pyright + `--verifytypes`, unit tests across the
  min/max matrix above, docs build with warnings as errors, package build +
  `twine check`.
- Never runs system tests; needs no YellowDog secrets.

### Release script
- **2.0.0 (and future releases) are released from `main`** after
  `next-version` is merged. The script's branch check requires `main` and that
  it is up to date with `origin/main`.
- The script pushes the tag to `origin` after the PyPI upload succeeds
  (builder's call).
- Runs **locally** with the user's existing credentials (`~/.pypirc`, Docker
  Hub login).
- Pre-flight checks, aborting on failure: clean working tree, correct branch,
  format/lint check, pyright, unit tests pass, version not already on PyPI,
  changelog has an entry for the version, tag doesn't already exist.
- Steps: tag → build → `twine check` → upload (option to target Test PyPI
  first) → build & push docs Docker image → print reminder to notify ops.
- Shows a summary and asks for confirmation before any irreversible/publishing
  step. Supports a dry-run mode.
- `RELEASING.md` rewritten around the script.

### Documentation
Audience: Airflow users new to YellowDog, YellowDog users new to Airflow, and
people new to both.
- **Concept primers:** Airflow (DAGs, tasks, operators vs sensors, XCom,
  connections, templating) and YellowDog (applications & keys, namespaces,
  work requirements, task groups, tasks, worker pools, compute requirement
  templates) — enough to use the provider, linking out for depth.
- **Quick-start:** install → create connection → minimal working DAG.
- **Per-component how-to** for each operator and sensor, with examples.
- **Templating & callables**, **error handling & troubleshooting** sections.
- **Changelog** including 1.x → 2.0 migration guide.
- **API reference** (autodoc) checked for accuracy against the code;
  docstrings reviewed (fix e.g. `ProvisionedWorkerPool` →
  `ProvisionedWorkerPoolProperties`).
- README / PYPI_README updated (Airflow 3 requirement, Python range).
- Docs build in CI with warnings as errors; publishing remains the Docker image
  flow.

### Tooling
- Builder's call (proposed, not objected to): replace black/isort/pyupgrade
  with `ruff` (format + lint, including pyupgrade-equivalent rules for py310);
  `make format` continues to be the single formatting entry point.
- Dev dependencies declared properly (e.g. `pyproject` optional-dependencies
  or updated `requirements-dev.txt`), replacing `mypy` with `pyright`.
- Fix Makefile `uninstall` target, which uses the wrong package name
  (`airflow-provider-yellowdog` → `yellowdog-airflow-provider`).
- Update `CLAUDE.md` to reflect new commands, testing, CI and release flow.

## Code review — known items to address

Initial read found (non-exhaustive; the full review must go beyond these):
- `AddPopulatedWorkRequirement` reverses the caller-supplied task group list
  in place (`wr.taskGroups.reverse()`); sequencing intent needs verifying
  against the SDK/platform and the mutation removed.
- `AddTaskGroupsToWorkRequirement` identifies newly added task groups by name,
  which can return IDs of pre-existing groups with the same name.
- `ProvisionWorkerPool.provisioned_worker_pool_properties` is typed optional
  but has no default.
- `YellowDogHook.get_conn` checks `host == ""` but not `None`.
- `ShutdownProvisionedWorkerPool` silently returns `None` for unexpected pool
  types.
- `AddTasksToTaskGroup` error message missing a space (`and'task_group_name`).
- Heavy use of `cast()` around templated fields; consider a cleaner typing
  pattern for "value or callable" fields.
- Sensors manually push XCom `return_value` alongside `poke`; consider Airflow
  3 idioms (e.g. `PokeReturnValue`, available in `airflow.sdk` on 3.1+).
- `get_*_by_id_or_name` utils are near-duplicates; consider consolidation.
- `YellowDogException` is a placeholder; decide whether provider errors should
  be more specific.
