# YellowDog Airflow Provider 2.0 Workflow Operators Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make "provision a pool, run work on it, shut it down" a safe three-task DAG: a `RunWorkRequirement` operator, deferrable waiting, cancellation on kill/timeout, run-stamped idempotent retries, setup/teardown pools, hook operations for TaskFlow, and Portal links.

**Architecture:** Pure helpers (run stamp, naming, retry decision, state resolution) live in `yellowdog_provider/utils/`; all YellowDog calls go through new typed `YellowDogHook` methods; one generic trigger (`YellowDogStateTrigger`) serves every deferrable wait; operators and sensors become thin wrappers that either poll (sync) or defer to the trigger and finish in `execute_complete`. Existing fine-grained operators/sensors stay and gain the shared behaviour.

**Tech Stack:** Python 3.12–3.14, Apache Airflow 3.1–3.4 (`airflow.sdk`, `airflow.triggers.base`), yellowdog-sdk ≥ 15.10.0, pytest, pyright strict, ruff, Sphinx.

**Spec:** `docs/superpowers/specs/2026-11-11-provider-2.0-workflow-design.md` (read it first; it is the authority).

- Branch `provider-2.0-workflow`; squash-merge to `next-version` only with the user's OK.
- Airflow ≥ 3.1 (`airflow.sdk` imports; version-conditional imports only where unavoidable and type-clean on both 3.1 and 3.4); Python 3.12–3.14; yellowdog-sdk ≥ 15.10.0.

- SDK objects used directly; no JSON/dict wrappers. SDK exceptions propagate except: YEL-13327 "invalid transition" on cancel, and best-effort cancellation on kill/teardown paths (log, never raise).
- Nothing may be left running after a DAG run ends: every path that creates a work requirement or pool must cancel/terminate it on failure, own timeout or kill.

- Cancel = abort running tasks (`abort=True`).
- Pool ready = `WorkerPoolStatus.IDLE` or `RUNNING`.
- YellowDog names: lowercase `a-z0-9_-`, ≤ 60 chars.
- Portal URLs: `https://portal.yellowdog.ai/#/work/<id>` and `https://portal.yellowdog.ai/#/workers/<id>`; base = API URL with leading `api.` host label → `portal.`; optional connection override "Portal URL".

- Plain `pytest`/CI never touch the platform; live tests keep run-tag naming and the cleanup sweep.
- `make format` after every Python change. Don't touch untracked `dag-test.py` or `CLAUDE.md`.
- Every breaking change gets a before/after entry in `docs/changelog.rst` "Breaking changes (migrating from 1.x)".

## Review Focus

1. **A fixed work-requirement name reused by another DAG run** (e.g. a daily DAG with `name="nightly"`): expected a fresh suffixed copy is submitted and the other run's work requirement is never adopted, resumed or cancelled. → Task 4 `test_submit_name_owned_by_other_run_gets_fresh_copy`; Task 9 `test_teardown_cancels_only_this_runs_work`.
2. **A deferred task killed on Airflow 3.1** (triggers have no `on_kill` there): expected the teardown shutdown cancels this run's unfinished work requirements, so nothing is left running. → Task 9 `test_shutdown_cancels_unfinished_run_work_requirements`, live in Task 13.
3. **Run IDs and DAG IDs with characters YellowDog rejects** (`manual__2026-11-11T10:00:00+00:00`, uppercase, dots, very long IDs, mapped tasks): expected a valid, stable, unique name ≤ 60 chars, and `-try<N>` still fits. → Task 3 `test_derive_name_sanitises_run_id`, `test_try_name_respects_limit`.
4. **Triggerer restart mid-wait**: expected the trigger rebuilt from `serialize()` resumes the same wait with the same deadline and states. → Task 5 `test_trigger_serialize_round_trip`.
5. **Connection host without an `api.` label** (custom host, IP, `localhost:8080`): expected no Portal link (never a wrong link) unless the "Portal URL" override is set. → Task 10 `test_portal_base_none_without_api_label`.
